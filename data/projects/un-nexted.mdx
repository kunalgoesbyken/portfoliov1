<Section kicker="For everyone" title="What it does">

Most React developers use Next.js as a black box. When a hydration error or a routing surprise appears, there is no mental model of what the framework did.

Un-nexted opens the box. Drop a React file into `src/pages/` and run one command: `about.tsx` becomes `/about` and `blog/[slug].tsx` becomes a dynamic route. Pages arrive as real HTML, which is good for search engines and first paint, with their data loaded on the server through `getServerSideProps`, just like the Next.js pages router. Then the browser takes over and the page becomes interactive.

It is a learning project, small enough to read top to bottom in one sitting. It deliberately leaves out caching, API routes and image optimisation, and says so. The full write-up is on the [blog](/blog/un-nexted).

</Section>

<Section kicker="For engineers" title="How it is built">

Four files, one per stage: `router.ts`, `build.ts`, `server.ts` and `client.tsx`, plus a shared `types.ts`. Bun is the runtime, bundler and package manager, and it runs TypeScript directly, so there is no Babel or webpack. The `typescript` package is only there for type checking.

<Diagram name="un-nexted-lifecycle" title="Request lifecycle" />

1. **Route.** At startup `Bun.Glob` scans `src/pages` for `.tsx` files, skipping `_app.tsx`, `_document.tsx` and nested files that start with an underscore. Each path becomes a URL pattern, compiled to a regular expression with a capture group per `[param]` segment. The first match in scan order wins.
2. **Build.** `startServer()` in `server.ts` initialises the router, then calls `buildClient()`. `Bun.build` bundles `client.tsx` for the browser as ES modules with code splitting. A plugin provides a virtual module, `unnexted:pages`, that maps each page's file path to a literal `import()`, so every page becomes its own chunk in `dist/`.
3. **Load.** For each request `renderPage` matches the path, imports the page module and awaits `getServerSideProps` with `params` and `pathname`. An unmatched path renders `404.tsx` with a 404 status. A failed import or a throwing data function returns a plain error page with a 500 status instead of crashing the server.
4. **Render.** `renderToString` from `react-dom/server` produces the HTML. The pathname, props and page file path go into a `<script id="__UNNEXTED_DATA__">` tag as JSON with `<` escaped as the Unicode sequence `\u003c`, so the data cannot close the script tag.
5. **Hydrate.** `Bun.serve` also serves the `.js` files from `dist/`. In the browser, `client.tsx` reads the data tag, looks up the page loader in `unnexted:pages`, imports only that chunk and calls `hydrateRoot` with the same props, so React attaches event handlers to the HTML it already has instead of re-rendering it.

<Highlights>
<Highlight title="A router from a glob" result="Zero configuration, dynamic segments included">
A directory tree becomes a list of URL patterns with named params, using the same file-name convention as the Next.js pages router. Catch-all routes and static-over-dynamic priority are not implemented.
</Highlight>
<Highlight title="Hydration that matches by construction" result="The same props drive both renders">
Hydration errors happen when the client renders different data than the server. Shipping the exact server props in the HTML makes the first client render identical.
</Highlight>
<Highlight title="Safe serialisation" result="Embedded data cannot close the script tag">
Data embedded in a script tag is a classic injection point. Escaping `<` in the serialised JSON closes it without a sanitiser dependency.
</Highlight>
<Highlight title="Page-level code splitting" result="The browser loads only the page it is on">
The generated page map uses a literal `import()` per route, which lets `Bun.build` emit a separate chunk for each page. Hydration then imports just the chunk for the current route.
</Highlight>
</Highlights>
