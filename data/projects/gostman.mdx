<Section kicker="For everyone" title="What it does">

Every team that builds an API needs a way to call it, check the answers and repeat those checks before each release. The popular tools put shared collections, data-driven runs, report export and secret managers behind a paid plan and an account, so teams end up keeping one copy of their requests in the app and another in their test suite.

Gostman is one free tool for all of it. You build requests in the app, or import them from Postman, Bruno, Insomnia, OpenAPI, HAR or curl, add checks such as "status is 200" or "the first item's userId is 1", and everything is saved as plain YAML files in a folder you can commit to Git.

The same files then work in three places. Send a request by hand from the desktop or web app. Run the whole folder with `gostman run` on every pull request and get a text, JUnit, JSON or HTML report. Or let a coding agent such as Claude Code or Cursor call your API through `gostman mcp`, without ever seeing your tokens.

Nothing is uploaded. The apps and the CLI talk only to the hosts you send requests to. The same download also does load testing, mock servers, OpenAPI linting, secret scanning and code generation in 21 languages, in 10 interface languages.

</Section>

<Section kicker="For engineers" title="How it is built">

One Go request engine owns variable substitution, auth, body encoding, cookies, redirects, proxies and certificates for 13 protocols. Every front end is a thin shell over it, so a request behaves the same on a laptop, in a browser and in CI.

<Diagram name="gostman-system" title="System architecture" />

Browsers block cross-origin requests, so the web build forwards through a small Go function on Vercel, or through `gostman relay` running locally. `gostman serve` hosts the web app and the proxy from one binary, published as a Docker image with every release.

Scripts use `test()` and `expect()` and run Postman and Bruno snippets as written. There is one JavaScript runtime: in the browser it runs in a fresh Web Worker per script, and in the CLI the same code is bundled and run inside goja, a JavaScript engine written in Go.

<Highlights>
<Highlight title="One scripting runtime, two hosts" result="400-request run: 3.9 s to 1.2 s, allocations down 74%">
Scripts from imported collections are untrusted, so each one gets a runtime no other script has touched. Booting a fresh runtime per script was the bottleneck, so up to four runtimes are booted ahead of time, while checks that run no user code share one.
</Highlight>
<Highlight title="Secrets a coding agent cannot read" result="Agents run real calls without ever seeing the values">
The MCP server fills in a secret only for an address where one of your own requests already sends it, and scrubs every response for that secret in raw, URL-encoded, base64 and JSON-escaped forms. Writes are checked against a revision so two agents cannot silently overwrite each other.
</Highlight>
<Highlight title="Huge responses without a frozen UI" result="20 MB JSON: DOM nodes 16,113 to 934, longest frame 271 ms to 90 ms">
The collection tree is windowed (33 rows in the DOM out of 5,258), JSONPath and extract rules run in workers with time limits, and large uploads stream instead of sitting in memory as base64. Pasting a 60,000-line body went from an 82.8 s freeze to a 12 ms key press.
</Highlight>
<Highlight title="Parallel folder loading, identical output" result="Opening 5,000 requests: 14.8 s to 5.4 s">
The old walk re-checked every parent folder for every file. One bounded pool of readers now reads the whole tree and assembles it in the original order, verified byte for byte against folders with broken files, duplicate ids, junctions and deep nesting.
</Highlight>
</Highlights>
