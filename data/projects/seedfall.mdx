<Section kicker="For everyone" title="What it does">

Software that stores data, such as databases, queues and replicated clusters, usually passes its tests and then loses data in production. The bug needs a power cut at one exact moment, or a network split at another, and an ordinary test almost never hits that moment. When production does, nobody can reproduce it.

Seedfall makes those moments happen on purpose, and makes them repeatable. You write a short workload that uses your service and says what must stay true, for example "every write I was told succeeded is still there after a crash". Then you run thousands of simulated trials. Seedfall crashes nodes, cuts power halfway through a write, fails disk syncs and splits the network, differently for each seed.

When something breaks you get a seed number. That seed reproduces the exact same failure on any machine, with a full trace and a timeline. Seedfall then shrinks a failure with dozens of faults down to the two or three that matter, and once you have a fix, it proves the fix by replaying the failure and sweeping fresh seeds.

It has already found real bugs in widely used projects, including NATS, hashicorp/raft, nutsdb and buntdb. One of them, in hashicorp/raft, leaves a node that panics on every restart after a badly timed power loss. Nine issues have been filed upstream and buntdb has already shipped a fix.

</Section>

<Section kicker="For engineers" title="How it is built">

The repository is one Go module. `sim` is the small library a workload imports for properties, operation history and `sim.Listen` and `sim.Dial`. `engine` is the simulator. `cmd/seedfall` is the CLI and the MCP server, `verify` and `report` produce proofs and triage output, and `seedfalltest` runs a sweep from `go test`.

<Diagram name="seedfall-system" title="Simulator architecture" />

One run of one seed goes like this:

1. `engine.Build` compiles each node package with the stock Go toolchain for `GOOS=wasip1`. `NewRunner` rewrites the wasm to add a call counter to every function (`instrument.go`) and compiles it once with wazero, cached under `.seedfall/cache`.
2. `Runner.run` builds a `world` for the seed: an in-memory file system and a network endpoint per node, seeded random streams for scheduling, network, disk and I/O faults, and a fault list generated up front.
3. `world.loop` runs exactly one node at a time. It takes the earliest of the next fault, restart or node wake-up, breaks ties with the seed and jumps virtual time forward, so ten seconds of `time.Sleep` cost nothing.
4. On wasip1 every source of nondeterminism leaves through three WASI calls, which the host implements: `random_get` is a ChaCha8 stream, `clock_time_get` is the virtual clock and `poll_oneoff` parks the node. A separate `seedfall` host module carries sockets, properties and operation history. Nothing needs a forked runtime or rewritten source.
5. wasip1 has no preemption, so after 4,194,304 counted calls without blocking the counter calls back into the host, which uses the Go runtime's own cooperative preemption.
6. The disk (`memfs.go`) keeps writes in a page cache and a crash keeps only synced data. Options add torn writes, reordered 4 KiB page writeback, strict directory durability, `EIO` on fsync, full disks, lost writes and bit flips. The network (`net.go`) gives TCP ordered streams with seeded latency, UDP that can reorder and drop, and one-way partitions. `sim.Listen` and `sim.Dial` reach it directly and an opt-in `net_overlay` patches Go's `net` package so plain `net/http` runs unchanged.
7. At the end the recorded history is checked with Porcupine, and a hash over every host call proves two runs of a seed were identical.

<Highlights>
<Highlight title="Determinism without forking Go" result="Same seed, same hash, 3 of 3 replays; run -check passes 200 of 200 seeds">
Reproducing a concurrent, distributed Go program byte for byte usually means patching the runtime. Routing every source of nondeterminism through three WASI calls made it possible with the stock toolchain. `seedfall run -check` runs each seed twice and stops at the first host call that differs.
</Highlight>
<Highlight title="Shrinking that never swaps bugs" result="33 faults to 2, one minute of virtual time to 991 ms, in 191 runs">
Delta debugging removes faults, then the workload is capped, the duration trimmed and each fault simplified. A candidate is kept only if it fails with the same class, node, property and message. Scheduling, network latency, disk tearing, fault timing and I/O faults each draw from their own seeded stream, so removing one fault barely disturbs the rest of the run.
</Highlight>
<Highlight title="A crash model with strict file system rules" result="Found that hashicorp/raft never fsyncs its snapshot directory">
Most storage bugs only appear under strict POSIX rules, torn writes or failing fsyncs, none of which a laptop disk shows. In raft's case, a crash after log compaction leaves an empty snapshot directory, and the node panics in `NewRaft` on every restart.
</Highlight>
<Highlight title="Proof that a pass means something" result="Every finding ships a root cause, a replay command and a verified patch">
`seedfall mutate` swaps in a deliberately broken disk, for example fsync as a no-op, and requires your checks to notice. `seedfall verify` replays the failing schedule against a patched copy and sweeps fresh seeds.
</Highlight>
<Highlight title="Built for coding agents" result="Found bugs in 2 of 9 AI-written crash-safe stores that passed their own tests">
`seedfall mcp` and four skills let an agent set up, run, shrink and prove a fix with no API key. In one experiment, three Claude models each wrote three crash-safe key-value stores; Seedfall found two that can refuse to open forever after a specific crash.
</Highlight>
<Highlight title="Fast enough for CI" result="200 seeds in 9.4 s on a laptop">
Seeds are independent, so `seedfall run -j N` runs N at once, and virtual time skips idle waits. A GitHub Action runs the same sweep in CI. The cost is booting: a large guest such as nats-server takes 0.1 to 0.3 s to start each node.
</Highlight>
