<Section kicker="For everyone" title="What it does">

Software that stores data, such as databases, queues and replicated clusters, usually passes its tests and then loses data in production. The bug needs a power cut at one exact moment, or a network split at another, and an ordinary test almost never hits that moment. When production does, nobody can reproduce it.

Seedfall makes those moments happen on purpose, and makes them repeatable. You write a short workload that uses your service and says what must stay true, for example "every write I was told succeeded is still there after a crash". Then you run thousands of simulated trials. Seedfall crashes nodes, cuts power halfway through a write, fails disk syncs and splits the network, differently for each seed.

When something breaks you get a seed number. That seed reproduces the exact same failure on any machine, with a full trace and a timeline. Seedfall then shrinks a failure with dozens of faults down to the two or three that matter, and once you have a fix, it proves the fix by replaying the failure and sweeping fresh seeds.

It has already found real bugs in widely used projects, including NATS, hashicorp/raft, nutsdb and buntdb. One of them, in hashicorp/raft, leaves a node that panics on every restart after a badly timed power loss. Nine issues have been filed upstream and buntdb has already shipped a fix.

</Section>

<Section kicker="For engineers" title="How it is built">

Each node is compiled with the stock Go toolchain for `GOOS=wasip1` and run as its own wazero WebAssembly instance inside one host process. On wasip1 the Go runtime is single-threaded and every source of nondeterminism leaves through three WASI calls, so Seedfall implements those three itself: random bytes come from a seeded ChaCha8 stream, the clock is virtual, and blocking parks the node until its next timer or packet. No forked runtime, no source rewriting, and new Go releases keep working.

Exactly one node runs at a time. The scheduler picks the earliest wake-up, breaks ties with the seed and jumps virtual time forward, so ten seconds of `time.Sleep` cost nothing. wasip1 has no preemption, so modules are instrumented with a call counter that triggers the Go runtime's own cooperative preemption after about four million calls without blocking.

The simulated disk has an explicit durability model: writes sit in a page cache, `Sync` makes them durable and a crash keeps only durable data. Options add torn writes, reordered 4 KiB page writeback, strict POSIX directory durability, `EIO` on fsync with Linux's post-2018 semantics, full disks, lost and misdirected writes and bit flips. The network gives UDP seeded reordering and loss, TCP ordered streams with seeded latency, and one-way partitions, all registered with Go's own poller so plain `net/http` runs unchanged.

<Highlights>
<Highlight title="Determinism without forking Go" result="Same seed, same hash, 3 of 3 replays; run -check passes 200 of 200 seeds">
Reproducing a concurrent, distributed Go program byte for byte usually means patching the runtime. Routing every source of nondeterminism through three WASI calls made it possible with the stock toolchain. `seedfall run -check` runs each seed twice and stops at the first host call that differs.
</Highlight>
<Highlight title="Shrinking that never swaps bugs" result="33 faults to 2, one minute of virtual time to 991 ms, in 191 runs">
Delta debugging removes faults, then the workload is capped, the duration trimmed and each fault simplified. A candidate is kept only if it fails with the same class, node, property and message. Every fault type draws from its own seeded stream, so removing one barely disturbs the rest of the run.
</Highlight>
<Highlight title="A crash model that matches real disks" result="Found that hashicorp/raft never fsyncs its snapshot directory">
Most storage bugs only appear under strict POSIX rules, torn writes or failing fsyncs, none of which a laptop disk shows. In raft's case, log compaction after an unsynced rename leaves an empty snapshot, and the node panics in `NewRaft` on every restart.
</Highlight>
<Highlight title="Proof that a pass means something" result="Every finding ships a root cause, a replay command and a verified patch">
`seedfall mutate` swaps in a deliberately broken disk, for example fsync as a no-op, and requires your checks to notice. `seedfall verify` replays the failing schedule against a patched copy and sweeps fresh seeds.
</Highlight>
<Highlight title="Built for coding agents" result="Found bugs in 2 of 9 AI-written crash-safe stores that passed their own tests">
An MCP server and four skills let an agent set up, run, shrink and prove a fix with no API key. In one experiment, three Claude models each wrote three crash-safe key-value stores; Seedfall found two that can refuse to open forever after a specific crash.
</Highlight>
<Highlight title="Fast enough for CI" result="200 seeds in 9.4 s on a laptop">
Seeds run in parallel jobs and virtual time skips idle waits, so a failing seed replays 0.99 s of simulated time in 0.1 to 0.3 s of real time.
</Highlight>
</Highlights>
